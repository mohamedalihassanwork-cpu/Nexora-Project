# Nexora Migration Convention: Expand and Contract Pattern

To ensure zero-downtime deployments and safe database schema evolution, all migrations in Nexora must follow the **Expand and Contract pattern**.

## The Pattern

When changing a database schema in a way that would break the running application (e.g., renaming a column, changing a column's type, or moving data), you must break the change into three distinct phases across multiple deployments:

### Phase 1: Expand
1. Add the new column/table/structure alongside the old one.
2. Ensure it is nullable (or has a safe default) so old application code doesn't fail when inserting.
3. Deploy the database migration.
4. Deploy the application update. The new application code should:
   - Read from the new structure if available, fallback to the old structure.
   - Write to **both** the old and new structures (dual-write).

### Phase 2: Migrate Data
1. Run a script or background job to backfill the data from the old structure to the new structure for all existing rows.
2. This is done while the application is running (which is safe because of the dual-write).

### Phase 3: Contract
1. Deploy an application update that only reads from and writes to the **new** structure.
2. Deploy a database migration that removes the old structure (e.g., `DROP COLUMN`).

## Example: Renaming a Column

**Bad Approach:**
```sql
ALTER TABLE users RENAME COLUMN old_name TO new_name;
```
*Why it fails:* Running application instances will crash because they are still selecting/inserting `old_name`.

**Good Approach (Expand and Contract):**
1. **Migration 1 (Expand):** `ALTER TABLE users ADD COLUMN new_name text;`
2. **App Update 1:** App writes to both `old_name` and `new_name`.
3. **Data Migration:** `UPDATE users SET new_name = old_name WHERE new_name IS NULL;`
4. **App Update 2:** App only uses `new_name`.
5. **Migration 2 (Contract):** `ALTER TABLE users DROP COLUMN old_name;`

## Current Baseline
The baseline migration (`0000_baseline.sql`) establishes the current state of the database and does not conflict with this pattern. Future migrations generated by Drizzle Kit must be manually inspected to ensure they do not perform destructive operations (like `DROP COLUMN` or `RENAME COLUMN`) in a single step.
